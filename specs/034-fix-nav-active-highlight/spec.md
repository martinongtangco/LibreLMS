# Bug Fix Specification: Admin "Courses" Nav Link Never Highlighted

**Feature Branch**: `bug/034-fix-nav-active-highlight`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User report: "the selected navigation highlight do not persist. example, login as
admin, go to courses. notice that the courses do not highlight to orange. then browse down,
select 2nd page and the selection becomes 'Browse Courses'."

## Root Cause

A single defect in the active-link detection IIFE in `src/Host/Pages/Shared/_Layout.cshtml`
(introduced by spec 020):

```js
var path = window.location.pathname;
var linkMap = {
    '/MyCourses/Index': 'my-courses',
    '/Courses/Index': 'browse-courses',        // (a)
    ...
    '/Admin/Courses/Index': 'admin-courses',   // (b)
    ...
};
for (var urlPage in linkMap) {
    if (path.indexOf(urlPage) !== -1 || ...) { // (c)
        ... activeLink.classList.add('active');
        break;                                 // (d)
    }
}
```

Two interacting flaws:

1. **Substring matching** (c): `path.indexOf(urlPage) !== -1` matches any URL that merely
   *contains* the key. `/Courses/Index` is a substring of `/Admin/Courses/Index` (at offset 6).
2. **Insertion-order iteration with early `break`** (a, b, d): `for...in` over an object
   literal iterates string keys in insertion order, so `/Courses/Index` ("Browse Courses") is
   checked before `/Admin/Courses/Index` ("Courses", admin). It matches first, wins, and the
   `break` stops the loop before the correct key is ever checked.

Consequence: on **every** admin Courses page URL — `/Admin/Courses/Index` (page 1) and
`/Admin/Courses/Index?pageNumber=2&...` (page 2+; identical pathname, only the query differs)
— the **Browse Courses** link receives the `.active` class (orange, via
`.navbar .nav-links a.nav-link.active { color: var(--accent) }`) and the admin **Courses**
link is never highlighted. This is exactly the reported behavior: after clicking the admin
"Courses" nav item, that item is not orange; the orange highlight sits on "Browse Courses",
which the user confirmed after selecting page 2.

**Evidence** — simulation of the shipped JS (same loop, same map order) against the page-1
pathname:

```
$ node -e "... same linkMap + loop ... path = '/Admin/Courses/Index'"
PATH /Admin/Courses/Index -> highlights: browse-courses
```

Secondary effect of the same flawed matching: **subpages** of a section match no key at all
(`/Courses/Detail`, `/Admin/Courses/Edit`, `/Admin/Learners/Create`, ...) and therefore
highlight nothing, violating spec 021 FR-006 ("The active admin page MUST be visually
indicated in the navigation").

No ADR is required (Principle X step 4): the root cause is a bug in a one-off client-side
script, not a design or architectural decision.

## Proposed Fix

Replace the substring matching with **section-prefix matching** in the same IIFE. Single
sentence (Constitution Principle II):

> A nav link is active when the current pathname equals its target path, or begins with the
> target path followed by `/` (i.e. the page is a subpage of that section); when several
> targets match, the longest (most specific) target wins.

Expected mapping for every current route:

| Pathname | Active link after fix | Before fix |
|---|---|---|
| `/MyCourses/Index` | My Courses | My Courses |
| `/Courses/Index` | Browse Courses | Browse Courses |
| `/Courses/Detail` | Browse Courses | (none) |
| `/Admin/Dashboard/Index` | Dashboard | Dashboard |
| `/Admin/Courses/Index` | **Courses (admin)** | **Browse Courses** ← bug |
| `/Admin/Courses/Index?pageNumber=2` | **Courses (admin)** | **Browse Courses** ← bug |
| `/Admin/Courses/Create`, `/Admin/Courses/Edit` | Courses (admin) | (none) |
| `/Admin/Enrollments/Index` | Enrollments | Enrollments |
| `/Admin/Enrollments/BulkEnroll` | Enrollments | (none) |
| `/Admin/Learners/Index` (+ `/Create`, `/Edit`) | Learners | Index ok; subpages (none) |
| `/Admin/Organizations/Index` (+ `/Chart`, `/Create`, `/Edit`) | Organizations | Index ok; subpages (none) |
| `/Admin/Upload` | Upload | Upload |
| `/`, `/Account/*`, `/Scorm/*`, `/Dev/*`, `/Error` | (none) | (none) |

The dead case-insensitive branch (`path.indexOf(urlPage.toLowerCase())`) is removed: every
URL in the app is generated by tag helpers with canonical casing, so no reachable pathname is
a lowercased route.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Admin Courses page highlights the "Courses" nav item (Priority: P1)

As an admin, when I open the Courses management page, the **Courses** nav item I clicked is
highlighted (orange), not "Browse Courses".

**Why this priority**: This is the reported defect — the highlighted link does not match the
page I am on, which misleads every admin.

**Independent Test**: Sign in as a SuperUser, open `/Admin/Courses/Index`, assert the
`[data-page="admin-courses"]` nav link has class `active` and
`[data-page="browse-courses"]` does not.

**Acceptance Scenarios**:

1. **Given** I am signed in as an admin with the Admin role view, **When** I open
   `/Admin/Courses/Index`, **Then** the admin **Courses** nav link has the `active` class and
   the **Browse Courses** nav link does not
2. **Given** I am on `/Admin/Courses/Index`, **When** I inspect the navbar, **Then** no other
   nav link has the `active` class

---

### User Story 2 — The highlight persists across pagination (Priority: P1)

As an admin, paging through the Courses list (and any other admin list) never moves the
highlight off the section I am in.

**Why this priority**: The user observed the wrong item ("Browse Courses") highlighted after
selecting page 2; pagination is the navigation path that exposed the bug.

**Independent Test**: With at least two pages of courses, click "Next →" and assert the
admin **Courses** link is still `active` and **Browse Courses** is not; repeat for the
Enrollments and Learners lists (URLs only, no data requirements beyond rendering).

**Acceptance Scenarios**:

1. **Given** I am on page 1 of admin Courses and **Courses** is highlighted, **When** I click
   "Next →" to page 2, **Then** **Courses** remains highlighted and **Browse Courses** is not
   highlighted
2. **Given** I navigate to `/Admin/Enrollments/Index` or `/Admin/Learners/Index` with a page
   query, **When** I inspect the navbar, **Then** the Enrollments / Learners link
   respectively is highlighted and no learner link is

---

### User Story 3 — Subpages keep their section highlighted (Priority: P2)

As a user, when I am on a subpage of a section (course detail, course edit, learner edit,
org chart, bulk enroll), that section's nav link stays highlighted.

**Why this priority**: Same root cause, same one-line rule; leaving it would strand the
subpages with no highlight at all (spec 021 FR-006).

**Independent Test**: Open `/Courses/Detail` for a seeded course → **Browse Courses** is
active; open `/Admin/Courses/Edit` for a seeded course → admin **Courses** is active.

**Acceptance Scenarios**:

1. **Given** I am on `/Courses/Detail` (any query), **When** I inspect the navbar, **Then**
   **Browse Courses** is highlighted
2. **Given** I am an admin on `/Admin/Courses/Edit` (any query), **When** I inspect the
   navbar, **Then** admin **Courses** is highlighted
3. **Given** I am on `/` (home) or `/Account/Login`, **When** I inspect the navbar, **Then**
   no nav link is highlighted

## Functional Requirements

- **FR-001**: The active nav link MUST be computed from `window.location.pathname` using
  exact match or section-prefix match (target + `/`); substring containment MUST NOT be used.
- **FR-002**: When several nav targets match a pathname, the longest target (most specific
  section) MUST win; exactly one nav link receives `active`.
- **FR-003**: On `/Admin/Courses/Index` (with any query string), the admin **Courses** link
  MUST have the `active` class and the **Browse Courses** link MUST NOT.
- **FR-004**: Changing pagination/filter/sort query parameters of an admin list MUST NOT
  change which nav link is active.
- **FR-005**: Subpages of a section MUST highlight that section's link (per the mapping
  table above).
- **FR-006**: Pathnames outside the nav sections (home, `/Account/*`, `/Scorm/*`, `/Dev/*`,
  `/Error`) MUST NOT highlight any nav link.
- **FR-007**: The fix MUST be contained to the layout's active-link IIFE — no new CSS, no
  server-side changes, no changes to the role toggle or hamburger behavior.

## Success Criteria

- **SC-001**: Playwright E2E: SuperUser on `/Admin/Courses/Index` → `[data-page="admin-courses"]`
  is `active`, `[data-page="browse-courses"]` is not (Story 1).
- **SC-002**: Playwright E2E: with two pages of courses, clicking "Next →" keeps the admin
  **Courses** link active on page 2 (Story 2).
- **SC-003**: Playwright E2E regression: every row of the mapping table highlights exactly
  the expected link (Story 3).
- **SC-004**: The existing Playwright regression set (at minimum specs 02, 04, 05, 07, 10,
  16) passes with no new failures.

## Assumptions & Constraints

- The active state remains client-side only (spec 020 design); the match uses the pathname,
  so query strings cannot influence it.
- Nav targets and their `data-page` keys are unchanged; only the matching rule changes.

## Out of Scope

- Adding/removing nav links, changing the role toggle or mobile menu.
- Server-side rendering of the active class.
- Visual design of the active state (already defined in `site.css`).
